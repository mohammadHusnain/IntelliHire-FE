# Decisions

Format: ID · decision · who · rationale. "Owner" = project owner. "Proposed" decisions were made by engineering judgement where the Doc is silent and can be reversed on request.

| ID | Decision | By | Rationale |
|---|---|---|---|
| D-001 | **Tally/ERP integration is deferred.** Nothing Tally-related is designed or coded until the owner reopens it. | Owner | The Doc has no Tally content; no source defines version, mechanism or entities. |
| D-002 | **PostgreSQL 16** (psycopg 3), not MySQL. | Owner (approved recommendation) | Doc says its design works on either; PostgreSQL enforces the "one pending invitation per company and email" rule in the database, has transactional migrations and stricter constraints. |
| D-003 | **Refresh token is returned in the JSON body**, not an httpOnly cookie. Token delivery stays in one place so a later move to cookies is contained. | Owner (approved recommendation) | Matches the Doc's endpoint contracts; frontend and API will likely sit on different sites, where cross-site cookies are unreliable; avoids CSRF handling. Mitigated by 15-minute access tokens, rotation and blacklisting. |
| D-004 | Django project `config/` + `apps/<name>/`; tests live inside each app; apps `jobs` and `applications` are created when their module starts. | Proposed | Follows the Doc's layout; no empty folders. Replaces the generic `src/modules/module-0N` sketch in the master instruction. |
| D-005 | `IntelliHire-backend` is the backend integration branch; work happens on `backend/foundation` and `backend/module-0N`; merges only after tests pass and owner approval; `main` is never touched without approval. | Proposed (per master instruction) | Isolates backend work from the frontend. |
| D-006 | Settings split `base/local/production/test`; env via django-environ; production fails fast on missing `ALLOWED_HOSTS`/`EMAIL_HOST`. | Proposed | Misconfiguration must not reach runtime. |
| D-007 | No Celery/Redis. Emails go out via `transaction.on_commit`; deadline closing is a management command; production throttle counters use Django's database cache (`createcachetable`). | Proposed | Doc marks Celery/Redis optional; per-process in-memory throttling would be inaccurate across workers. |
| D-008 | `/api/docs/` and `/api/schema/` are served only when `API_DOCS_ENABLED=True` (default off in production). | Proposed | Avoid publishing the API surface by default. |
| D-009 | Error shape = DRF default plus `code` on general errors; a bare list-style `ValidationError` is wrapped as `non_field_errors`; `/api/` 404/500 return JSON without internals. | Proposed (Doc: "keep DRF's default shape") | Predictable errors for the React client. |
| D-010 | Pagination: page size 20, optional `page_size` up to 100. | Proposed | Doc specifies 20 only. |
| D-011 | Database integrity by constraint: lowercase email CHECKs, enum CHECKs on choice fields, case-insensitive unique company name, partial unique pending invitation; CHECKs on nullable columns must test `IS NOT NULL`. | Proposed | Application-level validation alone can be bypassed; a test exposed the NULL pitfall. |
| D-012 | `User`: UUID PK, `is_active` derived from `status == active`, users created only through the manager or services (Django admin "add user" disabled). | Proposed | Keeps profile/company records consistent; implements "only active users can log in". |
| D-013 | Private files use `STORAGES["private"]` (no URL, outside media root); images use the default storage; every upload gets a random name; validators check extension, size and magic bytes. | Doc §4.3 + Proposed | Production swaps the alias to a private Azure container by configuration. |
| D-014 | The Foundation migration contains all seven starting models (User, CandidateProfile, Education, Experience, Company, CompanyMember, StaffInvitation). | Doc ("Project setup" step 1) | Company sign-up in Module 1 needs the company tables. |
| D-015 | `send_email_on_commit` catches only SMTP/OS delivery errors, logs without recipient addresses, and lets programming errors raise. Module is `common/mail.py` (not `email.py`, to avoid shadowing the standard library name). | Proposed | Classified error handling; no PII in logs. |
| D-016 | Image upload: JPG/PNG, ≤ 2 MB (Doc), messages "Only JPG and PNG images are accepted." / "Image must be 2 MB or smaller."; size message for CV: "File must be 5 MB or smaller." | Doc limits; messages proposed | Doc gives limits, and wording only for the CV type error. |
| D-017 | Dependencies are added when first used: `pypdf` and `python-docx` arrive with Module 1's CV text extraction; `django-storages[azure]` with production storage. Tested on Python 3.13. | Proposed | No unused dependencies. |
| D-018 | The Doc is stored at `documentation/source/` and these files summarise it with section references. | Proposed | Session continuity and traceability. |
| D-019 | Until Module 1 ships `StatusAwareJWTAuthentication`, the default authentication class is SimpleJWT's `JWTAuthentication`; Foundation exposes no authenticated endpoints. | Proposed | The status-aware class belongs to Module 1 (Doc §1.5). |
| D-020 | Field lengths where the Doc is silent: phone 20, headline 150, location 150, job title 100, grade 50, URLs 300. | Proposed | Reasonable bounds; changeable by migration. |
| D-021 | Company sign-up blocks free-email domains only through `COMPANY_EMAIL_BLOCKED_DOMAINS` (empty by default). | Owner (Q4 default) | Doc calls the rule optional. |
| D-022 | Platform admins can suspend and reactivate users (`/api/platform-admin/users/<id>/suspend|reactivate/`). Not allowed on oneself or another platform admin. Suspending blacklists all of the user's refresh tokens. Reactivation recomputes the status from facts (unverified → `pending_verification`; company user → by company status; else `active`) because the previous status is not stored. | Owner (Q8 default) | FR-75; the admin Users page needs it. |
| D-023 | The profile CV is served by `GET /api/auth/profile/resume/` for the owner only (attachment, `no-store`); `PUT` returns that relative path as `resume`. | Owner (Q9 default) | A relative path avoids proxy-dependent absolute URLs; the frontend must send the Bearer header to fetch it anyway. |
| D-024 | No user deletion in Phase 1. | Owner (Q10 default) | Not in the Doc. |
| D-025 | Sign-up follows the Doc (name, email, passwords; no login until verified). `CandidateProfile` gains `bio` (≤ 400), `target_role` (free text ≤ 100), `experience_level` (`entry`/`mid`/`senior`), `portfolio_url`, and `resume_original_name`. | Owner (Q13/Q14 default); `resume_original_name` proposed | Matches the frontend profile page; original name is needed for downloads, as for applications. |
| D-026 | Upload rules follow the Doc: CV PDF/DOCX ≤ 5 MB (the frontend's `.doc` is rejected); images JPG/PNG ≤ 2 MB. | Owner (Q18 default) | |
| D-027 | Company sign-up (serializer, service, view) lives in the `companies` app and is routed at `/api/auth/register/company/`. Helpers it needs come from `accounts`. | Proposed | `accounts` never imports `companies`; the model graph stays acyclic. |
| D-028 | Role, status, company-status and member-role enums live in `apps/common/choices.py`. | Proposed | Permission classes in `common` need them without importing feature apps. |
| D-029 | Login does not call Django's `authenticate()`: it would make a wrong password and a non-active account indistinguishable. Credentials are checked first, then the status; an unknown email still hashes a dummy password to equalise timing. | Proposed | Doc requires distinct 401 and 403 responses. |
| D-030 | Refresh rotation is explicit: the user is reloaded, must be `active`, the old token is blacklisted under a row lock, and a new pair is issued with claims from the database. | Proposed | SimpleJWT's built-in rotation keeps stale `role`/`full_name` claims, skips the status check and can issue two pairs for one token under concurrency. |
| D-031 | Throttles key on the client IP taken with `NUM_PROXIES` (default 0: `X-Forwarded-For` is ignored). Added scope `password_reset_confirm` (10/hour). Change-password reuses the `login` rate (5/min per user) to limit old-password guessing. | Proposed (resolves Q6) | DRF's default trusts `X-Forwarded-For`, which lets clients dodge limits. |
| D-032 | Phone numbers: digits, spaces, `+`, `-`; 7–15 digits (the Doc's application rule), applied to profile and company-admin phone. | Proposed | One rule everywhere. |
| D-033 | Limits where the Doc is silent: at most 20 skills (≤ 50 chars each, de-duplicated case-insensitively), 50 education rows, 50 experience rows, years 1950 to current year + 10. | Proposed | Bounds abuse; skill cap matches the frontend. |
| D-034 | CV text extraction: at most 30 PDF pages, 15,000 characters, DOCX refused above 50 MB uncompressed; NUL bytes removed. Any parser failure yields empty text and a log line with the exception type only. This is the one place a broad `except` is used, because the parsers read untrusted files. | Proposed (Doc: extraction failure must not fail the upload) | |
| D-035 | Multipart bodies above 12 MB are refused from `Content-Length` before storage (`LimitedMultiPartParser`, default parser). | Proposed (Doc §4.2 cap ≈ 12 MB) | Stops a large upload from filling disk before the 5 MB check. |
| D-036 | The "new company awaiting review" email to platform admins is sent in Module 2 (Doc §2.5), not at sign-up in Module 1. | Proposed | Keeps TC-03's two emails exact and puts it with the admin tooling. |
| D-037 | Known limitations: password-reset requests can reveal account existence through response time (mail is sent in-request; no task queue); login throttling is per IP, not per account; an access token stays valid up to 15 minutes after logout, password change or reset (suspension and deactivation are immediate); expired rows accumulate in the token tables until `python manage.py flushexpiredtokens` is scheduled. | Proposed | Accepted for the project scope; revisit with a deployment target. |
| D-038 | Module folders are named `apps/Module1_Authentication` and `apps/Module2_CompanyManagement` (owner's "Module1-name" convention, with an underscore because hyphens cannot be imported). Django app labels stay `accounts` and `companies`, so table names, migrations and `AUTH_USER_MODEL` are unchanged. Later modules follow `Module3_…`, `Module4_…`. | Approved (owner) | Verified by the unchanged test count and `makemigrations --check` after the rename. |
| D-039 | Suspending a company stores its reason in a new `suspension_reason` column (migration `companies.0002`, Q21); a CHECK requires it while `status = 'suspended'`. Suspend and reject reasons need at least 10 characters (Doc §2.4 for reject, same rule for suspend). Reactivation clears it. Only an `approved` company can be suspended. | Approved (owner, default) | Mirrors the existing `rejection_reason` rule. |
| D-040 | Accepting an invitation requires the company to be `approved` at that moment, creates the user already `active` and email-verified (the invitation proves the mailbox), and returns `{email, status}` without tokens. The invitation row is locked while it is consumed so concurrent accepts create one user. | Proposed | Avoids issuing a session from a public unauthenticated endpoint. |
| D-041 | The rejection email links to `FRONTEND_URL/resubmit-company`; the invitation email to `FRONTEND_URL/accept-invite?token=`. Resubmission re-derives the founder's status from verification state and the new company status (so an unverified founder returns to `pending_verification`, not `pending_approval`). | Proposed | The frontend has neither page yet (Phase 5). |
| D-042 | The platform-admin company list uses the project's standard pagination; the member and invitation lists are unpaginated. | Proposed | Review queues grow; a single company's team does not. |
| D-043 | No platform-admin read access to jobs or applications in Phase 1 (Q7), no auto-approval of companies (Q19), and Doc enums/fields win over the frontend's company fields (Q15). | Approved (owner, defaults) | |
| D-044 | Member admin rows are locked in primary-key order inside one transaction, so two admins deactivating each other at once cannot both succeed; the company always keeps one active admin. A member cannot change their own role or active flag (Doc §2.6); job title is editable. | Proposed | Verified with a real two-thread test. |
| D-045 | Invitation tokens: 32 random bytes (`secrets.token_urlsafe`), only the SHA-256 hash stored; resend rotates the token (the old link dies) and resets the 7-day expiry; one pending invitation per (company, email) is enforced by a partial unique index; expired invitations are marked on read. | Proposed | A database leak does not leak usable links. |
| D-046 | The founder's approval email goes to the founder's account email; platform-admin notifications go to every `active` platform admin. Approving a founder whose email is still unverified leaves them `pending_verification`. | Proposed | Doc §2.5 does not name recipients beyond "company admin" and "platform admins". |
| D-047 | Company-side views read `request.user.company_membership.company`; a user outside a company or in a non-approved company is refused by `IsCompanyUser`/`IsCompanyAdmin` before any query runs. | Proposed | One place enforces tenancy. |
